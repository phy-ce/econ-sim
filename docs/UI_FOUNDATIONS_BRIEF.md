# 화면 기초 정의 지시서 (화면 작업자용, 2026-11-06)

사용자 지시: 디자인 시스템 초안01(Crown Ledger, `553d59c`)의 모양이 나쁘다는 뜻이 아니다. 뭘 만들어야 하는지, 디자인의 기초부터 규정해야 하는데 그 궁리가 없었다. 세상에서 널리 쓰이는 디자인 시스템을 참고해 기초를 먼저 정한다.

이 문서는 답이 아니라 **밝혀야 할 질문의 목록**이다. 답은 화면 작업자가 쓰고, 사용자가 정한다.

## 1. 지금 무엇이 빠졌나
초안01은 지금 게임 화면에서 부품 목록을 가져와 색·간격·모양을 새로 입혔다 (`design-system/README.md` "The existing game supplied the inventory"). 그래서 순서가 거꾸로다.

디지털청 디자인 시스템(DADS)은 디자인 시스템을 디자인 원칙, 컴포넌트 정의, 가이드라인, 디자인 언어의 묶음으로 정의한다. 자기 프로젝트용 시스템(로컬 디자인 시스템)은 **브랜드·커뮤니케이션 규정 → 스타일 정의 → UI 컴포넌트 조정** 순서로 만들기를 권하고, 화면 설계서를 병행해 발견한 것을 컴포넌트 정의에 되돌린다. 계획·정보 설계 담당은 정보 컴포넌트로 정보 설계부터 와이어프레임까지 간다.

초안01에서 이 순서가 빠져 생긴 일 (모두 코드에서 확인):
- **게임의 핵심 도구가 부품에 없다.** 분해, 핀, 미리보기, 지도 레이어, 차트가 없다. 있는 것은 버튼·탭·카드·장부 행처럼 어느 앱에나 있는 것이다.
- **밀도 값이 게임의 일과 맞는지 따지지 않았다.** 장부 행 44px이면 420×560 창에 약 10행 들어간다 ((560−제목 40−탭 40)÷44, 제목·탭 높이는 오버홀 09의 가정). 오버홀 09의 몫의 장부는 접어도 15행, 펴면 18행이고 24px 행을 가정했다.
- **색의 뜻을 정하기 전에 색을 골랐다.** 조작색 `--ds-primary #28564f` 와 이익색 `--ds-positive #276447` 이 거의 같은 초록이다. `--ds-crown` 과 `--ds-brass` 는 같은 값이다. 계층 색·왕국 색은 `tokens.css` 에 없다.
- **정체성을 정하지 않고 바꿨다.** README는 이 게임을 "parchment and pixel-art style"이라 하는데 초안은 픽셀 숫자를 고정폭으로 바꿨다. 좋다 나쁘다가 아니라, 이 게임의 얼굴이 무엇인지 정한 적이 없다.

## 2. 밝혀야 할 것
순서대로 푼다. 앞이 정해져야 뒤가 정해진다. "참고"는 그 시스템이 무엇을 규정하는지 보는 것이지 값을 베끼는 것이 아니다. DADS는 공공 웹서비스용이고 이것은 1920×1080 한 화면의 경영 게임이다.

### A. 무엇을 만드는가 (제품 정의)
- 이 시스템은 무엇을 위한 것인가. 게임 화면 전체인가, 사전·보고서·홍보 페이지까지인가.
- 누가, 어떤 상황에서 쓰나. 몇 시간씩 숫자를 읽는 사람인가, 처음 온 사람인가. 둘이 부딪히면 누구 편인가.
- 플레이어가 화면에서 하는 일을 동사로 적으면 무엇인가. 그 일마다 어느 정보가 필요한가.
- 참고: DADS 브랜드·커뮤니케이션 규정, 역할별 사용법. 재료: 오버홀 01 1~3장, 09 1장 (경험 한 줄, 결정 D1~D5).

### B. 디자인 원칙 (판단이 갈릴 때 쓰는 기준)
- 3~5개로 줄인다. 각각 "A보다 B"처럼 무엇을 포기하는지 드러나야 한다. "깔끔하게" 같은 말은 판단을 못 가른다.
- 서로 부딪힐 때의 순서도 적는다.
- 참고: DADS 접근성 우선. 재료: 오버홀 01 4장 기둥과 금지 항목, CLAUDE.md "화면에는 설명 문구를 넣지 않는다".
- 시험: 지금까지 사용자가 지적한 사례(건설 창이 난잡하다, 아이콘이 작다, 창이 무겁다)를 이 원칙으로 판정해 본다. 답이 안 나오면 원칙이 약한 것이다.

### C. 정보 구조 (무엇이 화면에 있는가)
- 게임에 있는 정보 객체는 무엇인가 (지역, 왕국, 건물, 상품, 인구, 회사, 법, 기술, 지표, 사건...). 객체마다 요약·목록·상세가 어떻게 생기나.
- 화면 유형은 몇 가지인가 (지도, 상시 칩, 주 창, 서브윈도우, 툴팁, 토스트). 각각 무엇을 맡고 무엇을 맡지 않나.
- 정보의 깊이는 몇 층인가. 어디서 어디로 내려가나.
- 참고: DADS 정보 컴포넌트, GOV.UK Styles·Components·Patterns 구분 (Patterns는 사용자의 일 단위다). 재료: 오버홀 09 3.2 층 L0~L4, UI_DESIGN 2장.

### D. 지킬 선 (접근성과 하한)
- 무엇을 절대 깨지 않나. 숫자로 적는다.
- DADS는 본문·UI 16px 이상, 14px 미만 원칙 금지이고 Dense 스타일도 14~17px다. 이 게임의 하한은 글자 10px다 (UI_DESIGN 4.3). 이 차이를 그대로 둘 이유가 있는가. 하한을 올리면 창에 몇 행이 들어가나.
- 대비: DADS는 글자 4.5:1, 비글자 3:1. WCAG 1.4.1은 색만으로 뜻을 전하지 않도록 한다.
- 포커스 표시, 키보드, 움직임 줄이기, 색각 이상은 어디까지 책임지나.

### E. 밀도
- 화면 유형별 밀도를 하나의 값이 아니라 **할 일에서 계산**한다. "이 창에 몇 행, 몇 열이 들어가야 하는가 → 행 높이 → 글자 크기" 순서다.
- 밀도는 몇 단계인가. 한 단계로 충분한가.
- 참고: DADS Dense(120~130% 행간, 관리 화면·데이터 표용), Oneline, 밀집 관리 화면은 엘리베이션 단차를 작게 둔다는 규칙. 재료: 오버홀 09 4.2 (추정치, 실측 필요), 사용자 기준 "좌우에 좁고 촘촘한 창, 가운데 지도".

### F. 색의 역할
- 먼저 색의 **역할**을 나눈다. 색상 값은 그다음이다. 역할마다 뜻 하나만 맡게 한다.
- 조작색, 이익·손실, 경고, 소유(왕실·저택·금융가), 계층, 왕국, 지도 레이어, 시대: 이것들이 서로 같은 색을 쓰지 않게 어떻게 나누나.
- **사용자가 정할 것:** 게임이 좋음·나쁨 색을 쓰는가. 지금 화면은 초록·빨강을 쓰고 (UI_DESIGN 4.1), 오버홀 09 R7·U5는 없애자고 제안했다 (미결정).
- 참고: DADS 키·공통·기능·액센트·시맨틱 분류와 "색과 뜻의 연결은 바꾸지 않는다". Carbon 레이어 토큰과 테마(토큰 이름은 그대로, 값만 바뀐다). Atlassian "토큰은 UI 결정을 이름 붙여 저장하는 단일 출처".

### G. 글자와 숫자
- 이 게임의 주 내용은 숫자다. 숫자의 글꼴·자리 맞춤·단위·소수 자리·줄임 규칙이 먼저다.
- 글자 스타일을 용도로 나눈다 (제목, 본문, 조밀한 표, 한 줄 조작). 한글·영문 폭 차이를 어떻게 다루나.
- 참고: DADS 스타일 이름 규칙(`Std-17N-170`: 분류·크기·굵기·행간)과 Display·Standard·Dense·Oneline·Mono 분류. 재료: UI_DESIGN 4.3, 5장.

### H. 표면과 층
- 지도 위에 창이 뜨고, 창 위에 서브윈도우, 그 위에 툴팁이 뜬다. 층이 몇 개이고 각각 무엇이 올라가나.
- 그림자만으로 구분하지 않는다 (DADS: 테두리 함께). 모달을 쓰는가, 쓰면 언제인가.
- 참고: DADS 엘리베이션 (레벨 정의, 오버레이는 2단계 위, 지나친 사용 금지).

### I. 그림과 아이콘
- 조작 아이콘(lucide)과 게임 그림(생성 아틀라스)의 역할 구분, 크기 단계, 위치 규칙, 라벨을 언제 붙이나.
- 장식은 어디까지 허용하나. 틀에만 두고 내용 칸은 비우는가.
- 참고: DADS 아이콘 (문서 구조의 위치로 4종 구분), 빅토리아3 개발 일지 30 (장식은 패널 틀·테두리·머리에 모으고, 내용 칸은 비운다).

### J. 문구
- 설명 문구 금지의 경계는 어디인가 (오버홀 12 Q5, V2-1~15 미결정). 라벨 낱말을 어떻게 고르나. 같은 뜻에 같은 말을 쓰는 어휘표를 어디에 둘 것인가.
- 참고: DADS 라벨 고정 컴포넌트(문구 흔들림 방지), Atlassian Foundations의 Content 항목. 재료: 오버홀 09 부록 A 어휘표.

### K. 조작과 상태
- 누르면 무엇이 일어나는지 모양으로 구분되는가: 세계를 바꾸는 조작(건설, 법) / 화면을 옮기는 탐색 / 정보만 보는 것. 되돌릴 수 없는 조작은 어떻게 다른가.
- 모든 부품이 가져야 할 상태 목록 (기본, 호버, 포커스, 눌림, 선택, 불가, 진행 중, 값 없음).
- 시간이 흐르는 화면이다. 값이 매일 바뀌면 무엇이 깜빡이고 무엇이 고정되나. 일시정지와 진행 중에 조작이 어떻게 다른가.
- 참고: 빅토리아3 개발 일지 29·30 (적절한 때 적절한 정보, 중첩 툴팁, Navigation 버튼과 Action 버튼 구분, 행동과 정보 분리).

### L. 부품을 넣는 기준과 운영
- 부품을 시스템에 넣는 기준은 무엇인가. GOV.UK는 제안 단계 Useful·Unique, 출시 전 Usable·Consistent·Versatile을 본다. 이 게임은 "A에서 적은 일이 필요로 하는가"로 시작한다.
- 게임 고유 부품 목록을 A~K에서 도출한다 (DADS 독자 컴포넌트). 초안01의 부품은 이 목록과 대조해 남길지 판정한다.
- 토큰과 기존 `styles.css`·`strategy.css` 의 이행 순서, 문서 소유자, 바뀌면 누가 무엇을 고치나.

## 3. 만들 것
`docs/UI_FOUNDATIONS.md` 하나. 장 구성은 위 A~L을 따른다.
- 칸마다 **[확정] [제안] [사용자 결정 필요]** 를 단다.
  - 확정은 CLAUDE.md, UI_DESIGN, 사용자 지시에 있는 것뿐이다. **오버홀 문서는 제안서이고 확정이 아니다** (00_INDEX). 숫자도 대부분 추정이다. 옛 내용도 있다 (예: 09의 창 7개, 지금 코드는 6개).
- 참고한 시스템은 직접 읽고 주소를 적는다. 아래 출처를 넘어서도 좋다 (Material은 이쪽에서 본문을 못 읽었다). 확인 못 한 것은 "확인 못 함"이라고 적는다.
- 사용자 결정 칸은 맨 앞에 모은다. 사용자는 **예를 들어 자세히** 설명받기를 원한다: 질문, 고르면 화면이 어떻게 달라지는지 실제 창으로 든 예, 추천과 이유. 10개 이내로 줄인다.
- 초안01 대조표: 초안의 결정마다 유지 / 바꿈 / 근거 없음.

## 4. 하지 말 것
- 이 단계에서 새 시안·토큰·컴포넌트를 만들지 않는다. 사용자가 기초 문서를 본 뒤 초안02로 간다.
- 초안01 코드와 게임 화면을 지우거나 옮기지 않는다.
- `docs/UI_DESIGN.md` 는 그대로 둔다 (담당이 따로 있다). 기초가 정해지면 옮긴다.
- 사용자 결정 칸을 대신 정하지 않는다.
