# 11. 로드맵 (오버홀 실행 단계)

작성 2026-10-30. 제안서이고 구현이 아니다. 단계 이름·순서·통과 조건의 정본은 01 문서 10장과 10 문서 7.2 이고, 이 문서는 그것을 실행 계획 한 장으로 묶는다. 둘이 어긋나면 01·10 이 맞다.
새 시뮬레이션은 돌리지 않았다. 실행 횟수와 시간은 01 10장 0b 표와 10 4.5 의 계산(1회 22~42초 가정)을 옮긴 것이고 실측이 아니다. "규모"는 내 추정이고 근거 없음이다.

---
## 0. 고정 전제와 읽는 법

- 틀은 **경제 샌드박스**다 (사용자 지시, 01 0장). 모든 단계는 승패·점수·강제 종료·게임이 정한 목표를 만들지 않는다. 얹는 층은 "끔 = 같음" 검사를 단다.
- 한 단계 = 한 브랜치 `wt-<이름>` + `premerge` (CLAUDE.md 커밋 절). main 병합은 typecheck, `test:core`, 화폐 보존·결정성, premerge ready 뒤에만 한다.
- 표기:
  - **[결정 대기: …]** 그 사용자 결정의 답이 있어야 시작하거나 병합할 수 있다. 결정 번호는 12 문서의 묶음 번호(Q1~)와 01 12장의 V·D 번호를 같이 쓴다.
  - **[기본값 진행]** 결정이 걸려 있지만 답이 없으면 기본값(지금 상태 또는 01 12.2 의 기본)으로 진행한다.
  - **동작**: 비트 동일(세계 결과가 한 비트도 안 바뀜) / 기준선 바뀜(결과가 바뀌지만 세계 규칙은 같음) / 규칙 바뀜.
- 규모 표기 (추정, 근거 없음): **작음** = 하루 안, **중간** = 2~4일, **큼** = 1~2주. 화면 작업은 화면 작업자 몫이라 sim 쪽 규모만 센다.

- **의존**: A0 (고정 저장 파일과 `samecheck` 가 0a 이전 코드로 만들어져 있어야 한다).
- **검증과 성공 기준**: 결정성·화폐 보존. 같은 저장에서 플레이어 명령 하나를 더한 세계와 안 한 세계에서 처방 뒤 첫 4주 동안 같은 후보 키가 같은 난수를 받는다. 병합 전: 20년 × 시드 1~4 × salt 0..3 = 16회로 설계 기준(시대 IV 첫 기술 연도 `tier4 ≥ 7`, 식량 하한, 화폐 해마다 1e-9) 통과표, 0a 직전 커밋 시드 1~4 결과 4회 나란히. 대조 측정(`burn` 쌍 대 salt 쌍)과 null(salt 0..7, 5년 × 시드 1·2). 설계 기준이 깨지면 0a 를 보류하고 원인을 조사한다 (D10-S11 기본).

## 5. 단계마다 같이 하는 일

- 커밋마다: `npm run typecheck`, `npm run test:core`. 비트 동일을 약속한 단계는 `samecheck` 같음, 기준선이 바뀌는 단계(0a, 0b′, 0.5)는 다름을 확인하고 새 기준 해시를 HANDOFF 에 적는다.
- 병합마다: premerge (테스트 → 네 관점 검토 → 고침 → 다시 테스트), 결과 ready 일 때만 main 병합과 푸시. 마지막은 main 을 합친 상태의 `golden:update` (D10-S9 답 뒤).
- 값·규칙을 정하면 같은 커밋에 근거(후보, 조건, 해마다 숫자 또는 보고서 id, 출처, 고른 이유, 약점)를 DESIGN 11장·해당 절·DECISIONS 에 적는다. 비교 결과는 "main <커밋>, N년 × 시드 S 에서 X 였다"로만 쓴다.
- 플레이어에게 보이는 것이 바뀌면 UI_CHANGES 0장 한 줄 + 2장 새 절. 사전(`encyclopedia.ts`)과 README 를 같이 고친다.
- 큰 단계가 끝나면 HANDOFF 를 갱신하고 보고서 앱 링크로 결과를 낸다 (그래프, 최소 1년 단위).
