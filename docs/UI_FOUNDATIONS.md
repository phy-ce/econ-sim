## A. 무엇을 만드는가

**[확정] 제품의 바탕:** 에스테라는 근세 왕국 경제 경영 게임이며 공개 브라우저 배포가 목표다(CLAUDE.md). 한/영·낮/밤 테마, 좁고 촘촘한 창과 가운데 지도를 유지한다(UI_DESIGN). 사용자 지시대로 Victoria 3와 다른 게임이다. 그 게임을 알아야 에스테라를 읽을 수 있다는 전제를 두지 않는다.

**[제안] 독립적인 설계의 기준:** 에스테라가 실제 제공하는 지역 시장·건물 방식·소유 지분·예산/법·시간 제어에서 과제를 정한다. 다른 게임의 대상 이용자·정치/외교 범위·패널 구성·학습 방식을 가져와 빈칸을 채우지 않는다. 참고 패턴마다 ‘에스테라의 어느 일을 돕는가’를 설명할 수 있어야 하며, 설명할 수 없으면 채택 근거가 없다.

**[제안] 경험 정의:** 플레이어가 세계의 숫자와 관계를 읽고, 자신이 바꿀 수 있는 것을 골라 실행하고, 시간이 흐른 뒤 결과를 비교할 수 있는 경제 작업 공간. 플레이어가 무엇을 성공으로 여기는지는 UI가 국고 점수나 자동 처방으로 대신 정하지 않는다. 대상 이용자의 숙련도·이용 시간은 조사 전 가설이다(Q2).

**[제안] 설계 순서의 참고:** DADS는 로컬 시스템을 브랜드·커뮤니케이션, 스타일, 컴포넌트 순서로 정리하고 정보 설계와 화면 검토를 연결한다. 이 문서에서는 그 절차를 참고하며 공공 웹서비스의 외형이나 값을 이식하지 않는다. [DADS 로컬 시스템](https://design.digital.go.jp/dads/guidance/local-design-system/), [역할별 사용법](https://design.digital.go.jp/dads/guidance/how-to-use/).

## B. 판단이 갈릴 때의 원칙

**[제안] 아래 다섯 원칙은 번호 순서로 적용한다.** 확정 규칙은 선결 조건이다. 앞 원칙을 깨면서 뒤 원칙을 달성하지 않는다. ‘깔끔함’ 자체는 합격 기준으로 쓰지 않는다.

| 순서·원칙 | 무엇을 양보하는가 / 판정 예 |
|---|---|
| [제안] 1. 그럴듯한 해석보다 값의 진실성과 플레이어의 판단 | [제안] 효율을 실제 가동처럼 보이게 하지 않는다. 손익·국고를 성공 점수로 만들지 않는다. 근거 없는 미리보기는 숨기거나 미제공 상태로 둔다. |
| [제안] 2. 한 화면의 양보다 읽고 누를 수 있음 | [제안] 아이콘·숫자·포커스를 줄여 행을 더 넣지 않는다. 작은 사람 아이콘 문제는 범례 문장을 추가하기 전에 식별 크기와 대비부터 해결한다. |
| [제안] 3. 매 순간의 전체 최신성보다 하는 일의 연속성 | [제안] 드래그·스크롤·선택을 세계 갱신이 끊지 않게 한다. 입력 중 재정렬을 미루더라도 대상과 명령 결과는 정확해야 한다. |
| [제안] 4. 모든 기능의 상시 노출보다 비교에 필요한 관계 | [제안] 건설 창에서 같은 건물의 새 건설·기존 관리가 이어지되, 모든 상세와 조작을 카드마다 펼치지는 않는다. 추가 클릭이 생기면 완료 시간·오류로 이득을 검증한다. |
| [제안] 5. 표현의 다양함보다 뜻이 반복해서 읽히는 문법 | [제안] 같은 상태에 매번 새 색·크기·여백을 만들지 않는다. 장식·정체성은 정보 구분과 충돌하지 않는 자리에서 표현한다. |

**[제안] 사용자 지적에 적용:** ‘난잡한 건설 창’은 4번으로 할 일과 상세를 나누고 2번으로 비교량을 확인한다. ‘작은 아이콘’은 2번 때문에 밀도 증가를 포기한다. ‘무거운 창’은 3번 때문에 숨은 본문 갱신·무관한 렌더를 줄이고, 1번 때문에 명령 결과와 값의 출처를 생략하지 않는다. 새 디자인이 예뻐 보여도 이 세 시험을 못 통과하면 채택 근거가 없다.

**[제안] 검증 참고:** 키보드로 동등한 일을 할 수 있는지, 포커스가 보이는지 각각 검증한다. 특정 초 수 안에 사라지는 포커스를 허용하지 않는다. [WCAG 키보드](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html), [포커스 표시](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html). 위 목표는 이 문서의 제안이며 게임에 대한 적합성 인증이 아니다.

## E. 밀도: 공간·시간을 써서 어떤 일을 가능하게 하는가

### E.1 다섯 축과 판정 순서

**[확정] 사용자 요구:** 밀도를 행 수로만 다루지 않고 시각·정보·디자인·시간·가치로 나눈다. 사용자가 준 ‘인터페이스 밀도’ 요약을 반영한다. **[제안] 해석:** ‘가치 ÷ 시간과 공간’은 설계 판단의 틀이다. 단위가 다른 항목을 나누어 객관적 단일 점수인 것처럼 계산하지 않는다. 네 표현/비용 축을 보고 마지막에 A의 일이 더 잘 끝나는지 판단한다.

| 축 | 이 게임의 기준 | 남길 것·줄일 것 / 확인 방법 |
|---|---|---|
| [제안] 시각 밀도 | [제안] 한 번에 보이는 양과 관계의 가독성을 함께 본다. 같은 행 수라도 이름·단위·값의 정렬과 그룹 경계가 중요하다. | [제안] 시세표의 상품명/가격/공급÷수요는 열을 맞추고 범위 선택은 표 밖에서 묶는다. 모든 행을 카드·테두리로 쪼개지 않는다. 한/영·긴 이름·음수·큰 값에서 오독과 눈의 왕복을 확인한다. |
| [제안] 정보 밀도 | [제안] 각 요소가 새 값·관계·상태·조작 가능성을 전달하는지 묻는다. 잉크가 적다고 무조건 좋지 않다. | [제안] 반복 장식·중복 표·뜻 없는 아이콘은 줄인다. 단위 머리글·합계 경계·선택 표시·정렬 단서·그룹 사이 여백은 남긴다. BuildingPops의 같은 표 두 번 표시는 새 정보가 없는 사례다. |
| [제안] 디자인 밀도 | [제안] 색·크기·굵기·간격의 차이마다 설명 가능한 역할이 있어야 한다. 필요한 결정/전체 결정이라는 관점으로 불필요한 변형을 찾는다. | [제안] 가까운 값은 같은 대상의 묶음, 같은 모양은 같은 역할, 전경은 지금 읽거나 조작할 대상이 되게 한다. 같은 상태의 창별 임의 색은 제거 후보. 소유·계층·경보를 한 강조색으로 합치는 것도 피한다(F). |
| [제안] 시간 밀도 | [제안] 창을 열어 비교하고 원인을 찾고 조작 결과를 확인하기까지의 시간·대기·왕복·실수를 본다. 렌더 시간만으로 대체하지 않는다. | [제안] 열기·탭·스크롤·드래그·상세 왕복·명령 확인을 각각 잰다. 의미 없는 전환 애니메이션, 숨은 창 갱신, 입력 중 재정렬을 줄인다. 입력 후 밀린 작업도 포함한다(E.4). |
| [제안] 가치 밀도 | [제안] 정확히 끝낸 플레이어의 일과 그 비용을 비교한다. 읽기·안전·실험 비교가 나아지면 공간·단계가 늘어도 채택할 수 있다. | [제안] 건설+관리를 첫 시험으로 삼는다. 건물 찾기→방식 비교→명령→실적 재확인에서 정답 대상·오류·되돌아감·완료 시간을 본다. 클릭 수 감소만으로 합격시키지 않는다. |

**[제안] 출처 한계:** 제공된 글의 원문 주소와 그 글이 말하는 터프티·게슈탈트·100ms 주장의 원 출처는 **확인 못 함**. 여기의 다섯 축은 제공 요약을 바탕으로 이 게임에 적용한 제안이며 정량 과학 법칙으로 인용하지 않는다. Google/Yahoo 시가총액 비교는 UI 밀도의 인과 근거로 사용하지 않는다.

### E.3 행·열 예산과 밀도 단계

**[제안] 계산 순서:** 일과 필요한 비교 항목 → 창의 실제 사용 가능 폭/높이 → 필터·머리글·조작 영역 차감 → 동시에 필요한 행/열 → 행 높이·글자 후보 → 판독/조작 검증. 작은 글자를 먼저 정하고 모든 기능을 밀어 넣지 않는다.

**[제안] 아래는 계산 예이며 현재 DOM 실측값이 아니다.** 560px 창에서 제목 40·탭 40을 가정하면 480px다. 여기에 필터 32·표 머리 24·내부 여백 합 16을 가정하면 본문은 408px다. 실제 창에서는 경계선·스크롤바·상태 줄도 측정해 뺀다. 오버홀의 15/18행과 제목·탭 치수는 설계 가정이며 확정 요구량이 아니다.

| 행 높이 후보 | 480px에 완전한 행 | 408px에 완전한 행 |
|---|---|---|
| [제안] 24px | [제안] 20행 | [제안] 17행 |
| [제안] 28px | [제안] 17행 | [제안] 14행 |
| [제안] 32px | [제안] 15행 | [제안] 12행 |
| [제안] 초안01 44px | [제안] 10행 | [제안] 9행 |

**[제안] 읽는 법:** 408px에서 15행은 행당 최대 27.2px, 18행은 약 22.67px다. 18행을 모두 독립 24px 조작으로 만들겠다는 요구와는 충돌한다. 글자를 줄여 숨기지 말고 고정 줄·접기·순수 표시 행/조작 행 분리·상세 경로·창 예산을 다시 검토한다. 14px×120%=16.8px 글줄을 24px 행에 넣을 수 있다는 산술만으로 긴 라벨이나 조작이 합격한 것은 아니다.

**[제안] 폭도 같은 방식으로 검토:** 420에서 테두리 2·좌우 여백 합 24·스크롤바 15를 가정하면 379px다. 이름 100 + 숫자 네 열 각 55 + 간격 네 곳 각 8 = 352px지만, 영어 이름 칸이 160이면 412px로 넘친다. 이때 단위의 머리글 이동·비교에 덜 필요한 열의 상세 이동·이름 전체를 읽는 경로를 검토한다. 행 수가 맞아도 가로 비교를 못 하면 실패다. 이 치수도 토큰 제안이나 실측이 아니다.

**[사용자 결정 필요] 단계 수:** Q4. **[제안]** 조밀한 비교용과 여유 있는 읽기/조작용의 두 용도를 먼저 시험한다. 전역 설정 두 개를 반드시 추가하자는 뜻은 아니다. 같은 행은 같은 문법을 쓰고, 건물 카드·인구 표·법 전환 조작에 같은 높이를 강요하지 않는다. DADS Oneline의 100% 행간은 클릭 영역 높이 100%나 모든 버튼 1줄 높이를 뜻하지 않는다. [DADS 타이포그래피](https://design.digital.go.jp/dads/foundations/typography/).

### E.4 시간 밀도: 이미 잰 것과 아직 모르는 것

**[제안] 기록의 사용 범위:** [UI_STATUS의 성능 재측정 정정](UI_STATUS.md)의 동일 sim tree `8802b7…` 전후 비교를 사용한다. Vite 개발 빌드, 헤드리스 Edge/CDP, CSS1920×1028, EN/dark, 같은 저장(tick14·83 인구 집단·56 건물, SHA256 앞 12자리 `9ca39450bfd5`), 주 창 6개, 각 12초 스크롤·드래그다. 변경은 `2e9eba6`의 숨은 본문 갱신 억제·memo·포매터 캐시·입력 중 스냅샷 반영 지연 등이다. React 시간은 기록된 누적 비용이며 한 번 누른 뒤 응답 시간과 같지 않다.

**[제안] 남은 비용:** 같은 비교에서 10× 입력 종료 후 0.5초에는 긴 작업 5개·합 460ms·최대 123ms가 남았다. 이후 sim tree `3e5d099…`의 후측정에서는 입력 중 0개, 정착 구간 2개·합 144ms·최대 83ms, 입력 없는 자동 갱신 12초에는 1개·55.92ms였다. **서로 sim 조건이 달라 두 후측정을 직접 개선율로 비교하지 않는다.** 메시지 수신 비용에는 별도 역직렬화 분리 계측이 없으므로 전부 JSON 파싱 비용이라고 부르지 않는다.

**[제안] 다음 판정 방법:** 같은 저장·코드 조건에서 창별 열기/탭/스크롤/드래그/상세 왕복을 분리하고 입력부터 다음 시각 피드백까지 중앙값·p95와 오류·완료 시간을 잰다. 1×/10×, 입력 후 정착, 큰 저장·배포 빌드도 구분한다. 제공 글의 ‘100ms면 동시처럼 느낀다’는 원 출처 확인 전 보편적 사실이나 합격선으로 쓰지 않는다. 100ms는 검토할 피드백 예산 후보일 뿐이다. 짧은 동작에 붙인 애니메이션이 일을 늦추는지도 따로 본다.

### E.5 가치 밀도의 첫 시험: 건설+관리

**[확정] 사용자 과제:** 건설과 건물 관리를 통합하는 방향 및 관련 2-92 지시가 있다. **[제안]** 현재 합쳐진 구현도 최종 정보 구조의 정답으로 간주하지 않고 첫 비교 대상으로 삼는다.

**[제안] 시험 시나리오:** 같은 지역의 기존 건물에서 실제 가동이 낮은 대상을 찾는다 → 일손/원료/방식 중 데이터로 확인 가능한 항목을 확인한다 → 기존 조정과 새 건설 후보를 비교한다 → 명령을 보내거나 취소한다 → 경과 후 같은 대상을 다시 확인한다. 새 건물만 짓는 짧은 과제도 함께 둬 통합이 단순 작업을 방해하지 않는지 본다.

**[제안] 기록:** 올바른 지역·건물·방식을 골랐는지, 정보 누락·오조작·되돌아간 횟수, 창 왕복, 클릭 수, 완료 시간, 읽은 수치의 단위/시점 이해를 기록한다. 한/영과 낮/밤을 같은 과제로 확인한다. 고정된 성공률·표본 수는 아직 정하지 않는다. 플레이어 시험 전에는 개선을 입증했다고 쓰지 않는다.

**[제안] 채택 기준:** 더 넓은 상세나 한 번 더 여는 단계가 있어도 잘못된 명령을 줄이고 비교를 끝낼 수 있으면 정당할 수 있다. 반대로 카드가 많아지고 클릭이 줄어도 원료·현재 값·후보를 잘못 읽으면 실패다. 이 판단이 네 축을 포장한 단순 ‘행 수 최적화’가 되지 않게 한다.

## F. 색의 역할

**[제안] 역할을 먼저 정의하고 실제 색상 값·새 토큰 이름은 이 단계에서 정하지 않는다.** DADS의 키·공통·기능·액센트·시맨틱 분류에서는 브랜드, 표면, 조작, 상태의 책임을 나누는 관점을 참고한다. [DADS 색](https://design.digital.go.jp/dads/foundations/color/).

**[제안] 의미의 일관성:** DADS는 시맨틱 색의 의미와 색상의 연결을 유지하면서 대비를 위한 밝기·채도를 조절하도록 한다. 이 게임도 승인한 역할의 뜻을 창·테마마다 뒤집지 않는다. 다만 DADS의 성공/오류를 경제적 이익/손실과 동일시하거나 그 팔레트를 자동 채택하지 않는다. [DADS 시맨틱 색](https://design.digital.go.jp/dads/foundations/color/).

| 역할 | 전달할 뜻과 중복 단서 |
|---|---|
| [제안] 조작·탐색·선택 | [제안] 누를 수 있음, 현재 선택, 키보드 포커스를 구분한다. 이익색 하나로 모두 표현하지 않는다. 라벨·버튼 경계·선택 표시를 함께 둔다. |
| [사용자 결정 필요] 이익·손실 | [사용자 결정 필요] Q5. [확정] 현행은 초록/빨강과 +/−다. [제안] 경제적 좋음/나쁨과 장부 부호를 분리한다. |
| [제안] 주의·위험 | [제안] 정지/조건 미충족/명령 실패의 종류·대상을 상태명과 아이콘으로 구분한다. 왕실 자산이 금색이라는 이유로 경고처럼 보이지 않게 한다. |
| [확정] 소유 | [확정] 왕실·저택·금융가를 아이콘+색으로 구분한다(UI_DESIGN 4.2). [제안] 소유 종류와 비율, 플레이어 소속, 왕국 정체성의 표시를 분리한다. |
| [확정] 계층 | [확정] 도넛·차트·표·막대가 계층별 같은 색을 쓴다(UI_DESIGN 4.1). [제안] 직종 이름·아이콘·순서도 유지하며 계층의 사회적 가치를 색으로 평가하지 않는다. |
| [확정] 왕국 | [확정] sim이 주는 왕국 색을 지도/소유 배지 띠에 쓴다(UI_DESIGN 4.1). [제안] 문장·이름·경계로도 식별한다. 테마마다 왕국의 뜻이 바뀌지 않는다. |
| [제안] 지도 레이어 | [제안] 영토 범주색과 부/생활수준의 양적 범례를 구분한다. 연속값의 밝기 변화가 조작 가능성을 뜻하지 않도록 범례·수치·선택 경계를 둔다. |
| [제안] 시대·장식 | [제안] 시대 정체성은 제목·그림·틀의 책임으로 둔다. 특정 시대를 좋음/잠금/위험 색으로 자동 평가하지 않는다. 별도 시대 팔레트의 필요는 아직 입증되지 않았다. |

**[제안] 충돌 방지:** 모든 범주에 전역적으로 유일한 색상 하나씩 주는 방식은 필요하지 않다. 같은 화면에서 같은 모양·색이 다른 뜻을 떠맡는 충돌을 피한다. 왕국 띠·소유 아이콘·부호·경고 형태처럼 위치와 표현을 분담한다. 유사 색이라도 별도 문맥에서 식별될 수 있고, 다른 색이라도 단서가 없으면 의미를 외워야 한다. 초안01의 조작/이익 초록과 왕실/황동 동일 값은 이 기준으로 재검토한다.

**[제안] 테마 운영의 참고:** Carbon은 표면의 레이어와 역할을 구분하고 테마에 걸쳐 역할을 유지한다. Atlassian은 토큰을 UI 결정의 이름 붙인 단일 출처로 설명한다. 승인된 뜻을 먼저 고정하고 낮/밤 값은 이후 검증한다. 새 색 묶음을 만드는 것으로 의미 충돌을 해결했다고 보지 않는다. [Carbon 색·레이어](https://www.carbondesignsystem.com/building-blocks/foundations/color/guidelines), [Atlassian Foundations](https://atlassian.design/foundations).

**[제안] 층의 뜻:** 위 표는 겹침 책임의 분류이며 새 z-index 값이나 고정 ‘7층’ 토큰이 아니다. 선택한 창의 메뉴/툴팁은 해당 표면 위에서 읽히고 다른 창을 가리는 범위를 제한한다. 정보의 깊이(C)가 늘어난다고 그림자를 계속 진하게 쌓지 않는다.

**[제안] 시각 경계:** DADS는 밀집 관리 화면에서 높이 차를 작게 쓰고, 그림자로 경계 대비를 대신하지 않으며, 오버레이를 기준 표면보다 두 단계 위에 두는 모델을 제시한다. 이 게임은 상대 겹침과 얕은 표현을 참고하되 숫자 레벨을 복사하지 않는다. 창 테두리·제목·내용 그룹으로 관계를 읽고 모든 행을 떠 있는 카드로 만들지 않는다. [DADS 엘리베이션](https://design.digital.go.jp/dads/foundations/elevation/).

**[제안] 툴팁 접근성:** 중첩 금지는 툴팁 위로 포인터를 옮기면 즉시 닫아야 한다는 뜻이 아니다. Esc 등으로 닫기, 내용을 읽는 동안 유지, 키보드 포커스로 접근을 검토한다. 호버/포커스 콘텐츠의 닫기·호버 가능·지속성 기준을 참고한다. [WCAG 1.4.13](https://www.w3.org/WAI/WCAG22/Understanding/content-on-hover-or-focus.html).

## J. 문구

**[확정] 본화면:** 설명 문구를 넣지 않고 라벨·숫자·막대·아이콘을 사용한다. 툴팁은 허용한다. 원리 설명은 README/사전 경로로 보낸다(사용자, CLAUDE.md, UI_DESIGN). 중첩 툴팁은 금지한다. **[사용자 결정 필요]** 객관적 상태와 해석 라벨의 경계는 Q7이다. 오버홀 12 Q5·V2 표는 승인 목록이 아니다.

**[제안] 공통 상태 목록:** 기본, 호버, 키보드 포커스, 누르고 있음, 선택됨, 조건 미충족, 처리 중, 완료/거절, 값 없음, 오래된 스냅샷/갱신 대기. 선택과 포커스는 함께 존재할 수 있다. 조건 미충족은 이유를 읽을 경로가 있어야 하며 단순 투명도만으로 표시하지 않는다. 처리 중에는 중복 명령 방지를 검토하고 확정된 세계 결과와 임시 입력값을 분리한다.

**[확정] 시간이 있는 화면:** 정지/진행·배속·하루 진행·‘~까지’와 정지 사유가 현재 UI 규칙에 있다. 창별 이력·포커스 복원도 지킨다(UI_DESIGN). **[제안]** 정지 중에는 정지한 세계 값임을 보존하고 입력 가능 여부는 해당 명령의 실제 조건으로 정한다. 진행 중에는 매일 갱신되는 값 때문에 행의 대상·입력값·열림 상태가 바뀌지 않게 한다. 렌더를 줄였다고 필수 결과 알림까지 지우지 않는다.

**[사용자 결정 필요] 갱신 정책:** Q9. **[제안]** 비교할 값의 기준 시점·주간 평균/현재 값 구분, 재정렬 적용 시점, 입력 중 지연을 정의한다. 기존 입력 후 200ms 반영 지연은 구현상의 선택이며 모든 조작의 보편적 디자인 값으로 확정하지 않는다. 세계가 계속 도는데 일시정지한 것처럼 보이게 하거나, 미리보기를 최신 실적으로 보이게 하지 않는다.

**[확정] 참고의 경계:** Victoria 3의 중첩 툴팁은 이 게임에 적용하지 않는다. **[제안]** 명령/탐색/정보의 구분은 위의 에스테라 과제에서 도출한 검토안이다. 타 게임의 조작 체계를 옮기는 논거로 쓰지 않는다.

## L. 부품을 넣는 기준과 운영

### L.1 채택 기준

**[제안] 순서:** A의 어떤 일을 돕는가 → 기존 표현으로 부족한 이유는 무엇인가 → 값·단위·상태·관계의 계약은 무엇인가 → 한/영·낮/밤·키보드·실시간 입력에서 쓸 수 있는가 → 반복 사용에 필요한 차이만 남겼는가. 이름·모양이 다른 기존 코드를 모았다는 이유만으로 새 부품을 만들지 않는다.

**[제안] 참고:** GOV.UK는 제안 단계에 Useful/Unique, 공개 전 Usable/Consistent/Versatile을 본다. 에스테라에는 ‘실제 일이 필요한가·기존 것으로 해결되는가·사용/상태 검증을 했는가’를 적용한다. 여러 정부 서비스에서 쓰였다는 조건을 이 저장소의 채택 요건으로 복제하지 않는다. [GOV.UK 기여 기준](https://design-system.service.gov.uk/community/contribution-criteria/).

### L.4 이행과 소유권

1. **[제안] 사용자 결정 기록:** Q1~Q9의 답과 유지할 현행 규칙을 분리한다. 오버홀 채택 여부를 문장별로 확인한다. 사용자 미응답을 동의로 간주하지 않는다.
2. **[제안] 의미/과제 검토:** 대표 과제·정보 객체·단위·상태·관계를 먼저 정하고 정보 구조/와이어프레임 검토로 부족한 정의를 되돌린다. 이번 단계에서는 실제 새 시안을 만들지 않는다.
3. **[제안] 토큰·부품 정의:** 승인된 역할과 읽기 예산에서 값·변형·상태를 도출한다. 기존 styles.css/strategy.css와 초안01을 동시에 전면 교체하지 않고 역할 대응표로 정리한다.
4. **[제안] 첫 적용/검증:** 건설+관리를 E.5의 첫 시험 대상으로 삼아 의미·판독·명령·언어/테마·키보드·성능을 확인한다. UI가 없는 sim 데이터는 화면에서 추측하지 않고 UI_STATUS에 요청한다.
5. **[제안] 점진 이행:** 검증된 책임부터 다른 창에 적용하고 중복 스타일은 참조·사용 여부 확인 후 별도 작업에서 정리한다. 전환 중에도 숫자 계약·이력·포커스·선택·기존 기능을 보존한다.

**[확정] 역할 경계:** 화면 작업자는 packages/sim을 고치지 않는다. UI_DESIGN은 UI/UX 담당이 관리하고 화면 작업자는 차이와 검증을 UI_STATUS에 남긴다. 사용자에게 속한 큰 방향 결정을 대신하지 않는다. **[제안]** 기초 변경 시에는 사용자 결정→정책 문서 담당→클라이언트 구현/검증→상태 기록 순서로 반영하고, sim 데이터/프로토콜 요청은 별도로 합의한다. 초안02는 이 문서를 검토한 뒤의 다음 단계다.
